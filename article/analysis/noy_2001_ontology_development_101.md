> **Source in `src/`:** [`../src/2001 Ontology Development 101: A Guide to Creating Your First Ontology.md`](../src/2001%20Ontology%20Development%20101%3A%20A%20Guide%20to%20Creating%20Your%20First%20Ontology.md)

Gindullina et al. (hereafter **Paper A**) built a hierarchical ontology of expert comments (Appendix A / Fig. A.6): four classes — behavior of the epidemic curve, containment measures, numerical parameters, peak position — each split into 2–4 subclasses, with corresponding loss-modification rules in Table A.2. This ontology serves as the *sole* control mechanism between free-text comments and LLM-generated loss modifications. The authors themselves admit the ontology «lacks sufficient detail to provide meaningful control over the generation process» and «is insufficient to ensure semantic transparency and explainability». The classifier that operationalizes the ontology was trained on 2,000 synthetic comments generated by DeepSeek-V3.1, and reached 0.811 accuracy on a held-out portion of that same synthetic distribution.

Noy & McGuinness (2001; hereafter **Paper B**) is the canonical tutorial for developing a first ontology in a declarative frame-based system. It codifies a 7-step methodology (determine domain/scope via competency questions → consider reuse → enumerate terms → define class hierarchy → define slots → define slot facets → create instances) built around a running wine-and-food example. Alongside the process it enumerates a set of design guidelines: no single correct ontology, iteration is essential, subclass = «is-a» relationship, singleton subclasses signal a modeling problem, more than a dozen direct subclasses signal missing intermediate categories, slots need cardinality/value-type/domain/range facets, multiple inheritance is legitimate for objects that are simultaneously two kinds, and — crucially — class distinctions should be introduced only when properties, restrictions, or relationships differ.

Paper B is not about PINN, LLMs, or epidemics; it is a 20-year-old baseline for what a *properly built* first-pass ontology looks like. The transferable thesis is sharp: **Paper A's Table A.2 + Appendix A is an ontology built without any of Paper B's 7 steps — no competency questions, no reuse consideration, no slot facets, no iteration — and every one of Paper A's documented failure modes (literal number insertion, unused variables, the peak-shift / BC-weight confusion in Fig. 4b) maps back to a specific skipped step; adopting Noy-McGuinness as a redesign checklist is the cheapest structural upgrade to Table A.2 available.**

## 1. Table A.2 as an ontology built without Step 1 (domain/scope + competency questions)

Paper B's first step is to write down **competency questions** that the ontology must answer, and use them to bound scope. Paper A defines its four classes by observed frequency of expert statement types — a data-driven bottom-up move, but not the same as scoping.

> **Quote (Noy & McGuinness):** *"One of the ways to determine the scope of the ontology is to sketch a list of questions that a knowledge base based on the ontology should be able to answer, competency questions (Gruninger and Fox 1995). These questions will serve as the litmus test later: Does the ontology contain enough information to answer these types of questions?"*

> **Quote (Gindullina et al.):** *"It is based on four basic classes, identified through an analysis of typical expert statements: 1. Behavior of the epidemiological curve (visual characteristics). 2. Taking into account measures to counter the spread of the epidemic. 3. Parameters or temporal dynamics of the epidemiological process (numerical characteristics). 4. Position of the epidemic peak on the time axis (in terms of incidence and mortality)."*

The Paper A ontology answers «which class does this comment fall into» — but not the more actionable questions: «given this comment, what modification is expected to move the forecast in the requested direction?», «what integrity constraints does this modification class preserve?», «what evidence would falsify the class assignment?». Competency questions of that form would have exposed the gap between comment class and modification effect that Fig. 4b makes visible. (Comparative inference)

## 2. Step 2 skipped: reuse of existing epidemic/PINN taxonomies

Paper B insists on Step 2 — consider what already exists — before building anything from scratch.

> **Quote (Noy & McGuinness):** *"It is almost always worth considering what someone else has done and checking if we can refine and extend existing sources for our particular domain and task. Reusing existing ontologies may be a requirement if our system needs to interact with other applications that have already committed to particular ontologies or controlled vocabularies. ... Medicine, for example, has produced large, standardized, structured vocabularies such as SNOMED and the semantic network of the Unified Medical Language System."*

> **Quote (Gindullina et al.):** *"The model, based on "bert-base-cased", was fine-tuned on a synthetic dataset of 2000 expert-like commentaries. This dataset was generated by DeepSeek-V3.1 using real expert comments to ensure representativeness"*

Two candidate reuses Paper A does not discuss: (i) the SIRD compartment vocabulary (S, I, R, D as canonical labels for term1..term4) is a public taxonomy that Table A.2 rewrites in local jargon; (ii) medical vocabularies (SNOMED, ICD) already partition disease-parameter changes (peak-shift, wave-count, containment) at a controlled-vocabulary level. Instead, Paper A synthesizes 2,000 comments from a single LLM (DeepSeek-V3.1) — same source as one of the three evaluated models — and trains a classifier on that closed distribution. This is not just a data-reuse miss; it is a circularity (see `dinara_comprehensive_review.md` §II). (Comparative inference)

## 3. Step 6 skipped: slot facets are the missing types on «Add penalty to term2»

Paper B is emphatic that slots must have facets: cardinality, value-type, domain, and range. A property without facets is under-specified; a system built on such slots will accept malformed values.

> **Quote (Noy & McGuinness):** *"Slots can have different facets describing the value type, allowed values, the number of the values (cardinality), and other features of the values the slot can take. ... Some systems allow specification of a minimum and maximum cardinality to describe the number of slot values more precisely."*

> **Quote (Gindullina et al.):** *"Add penalty to term2. Add penalty to term1. Add penalty to term4. Add penalty to term3. ... Modification of other function components is prohibited."*

Table A.2's Class 1 permits four modifications, each phrased as «Add penalty to term \(k\)». Nothing in the ontology specifies (i) the value-type of «penalty» (is it a coefficient? a functional form? both?), (ii) the cardinality (one penalty per term? at most one? multiple additive?), (iii) the range of the numeric coefficient (bounded to what interval? in what units?). Paper A then documents literal-number insertion — «meta-llama/Llama-3.3-70B-Instruct model exhibits a tendency to literally include these numerical parameters in the loss function without sufficient semantic adaptation» — as a systematic failure. In Noy-McGuinness terms, this is exactly what happens when Step 6 is skipped: values fill in without facet constraints. (Comparative inference)

## 4. Single-class assignment vs multiple inheritance

Paper B's wine-ontology example uses multiple inheritance: Port is both a red wine and a dessert wine, inheriting slots from both. Paper A's classifier forces exactly one (class, subclass) pair per comment, mediated by expert confirmation.

> **Quote (Noy & McGuinness):** *"Most knowledge-representation systems allow multiple inheritance in the class hierarchy: a class can be a subclass of several classes. Suppose we would like to create a separate class of dessert wines, the Dessert wine class. The Port wine is both a red wine and a dessert wine. Therefore, we define a class Port to have two superclasses: Red wine and Dessert wine."*

> **Quote (Gindullina et al.):** *"After automatic classification, the expert confirms the correctness of the assigned class and subclass. This validation step is critical to minimizing errors due to natural language ambiguity."*

Consider a comment such as «shift the peak by 7 days and make the post-peak decline sharper». This is simultaneously Class 4 (peak position) and Class 1 (behavior of the curve). Under Paper A's ontology, the expert must choose one — losing information. Under Noy-McGuinness, this comment would be a multiple-inheritance instance, receiving slots from both parent classes. The failure mode this enforces in Paper A is subtle but consequential: comments that mix intent get truncated to one axis before the LLM sees them. (Comparative inference)

## 5. Singleton and over-populated subclasses: Table A.2 checks

Paper B provides two structural diagnostics for a class hierarchy: singleton subclass = probable modeling error; more than a dozen direct subclasses = missing intermediate categories.

> **Quote (Noy & McGuinness):** *"If a class has only one direct subclass there may be a modeling problem or the ontology is not complete. ... If there are more than a dozen subclasses for a given class then additional intermediate categories may be necessary."*

> **Quote (Gindullina et al.):** *"Class 3: Parameters or temporal dynamics of the epidemiological process (numerical characteristics) — 3.1 Time discrepancy — 3.2 Discrepancy in quantity"*

Table A.2's Class 3 has exactly two subclasses (time vs quantity). Under Paper B's heuristic this is not by itself an error — it is above the singleton threshold — but the coarseness contrasts with Class 1's four subclasses. More importantly, Class 3's modifications («Add time-based penalty to term2», «Add penalty to term2 considering quantitative characteristics») do not carry different constraints — both apply only to term2. If two subclasses share a slot-modification pattern, they are structurally the same class (Paper B §4.4: introduce a subclass only when it has «additional properties ... restrictions different from those of the superclass, or ... different relationships»). Class 3 fails that test. (Comparative inference)

## 6. Iteration: ontology development is inherently iterative

Paper B's fundamental rule 2 — ontology development is an iterative process — is explicit and repeated.

> **Quote (Noy & McGuinness):** *"Ontology development is necessarily an iterative process. ... After we define an initial version of the ontology, we can evaluate and debug it by using it in applications or problem-solving methods or by discussing it with experts in the field, or both. As a result, we will almost certainly need to revise the initial ontology. This process of iterative design will likely continue through the entire lifecycle of the ontology."*

> **Quote (Gindullina et al.):** *"Manually defining rules for all possible expert comments is infeasible, so we structure comments using a hierarchical ontology. It is based on four basic classes, identified through an analysis of typical expert statements ... The model, based on "bert-base-cased", was fine-tuned on a synthetic dataset of 2000 expert-like commentaries."*

Paper A fixes the ontology once (before generating the synthetic training set) and then treats it as frozen. There is no described feedback loop where 25–27% compliance data is used to refine the ontology; no revision after Fig. 4b/c were observed. Paper A's Future work names «class-subclass-specific modification templates» as an extension — but templates *of* the same fixed 4-class hierarchy, not iteration *on* the hierarchy. Iteration is exactly the step that would connect observed failures to ontology changes. (Comparative inference)

---

## 7. Class vs slot: «position of the epidemic peak» as slot or class

Paper B §4.5 gives a rule of thumb for when a distinction should become a new class vs a slot value: introduce a new class when the distinction implies different slots, restrictions, or relationships in other classes.

> **Quote (Noy & McGuinness):** *"If the concepts with different slot values become restrictions for different slots in other classes, then we should create a new class for the distinction. Otherwise, we represent the distinction in a slot value. ... If a distinction is important in the domain and we think of the objects with different values for the distinction as different kinds of objects, then we should create a new class for the distinction."*

> **Quote (Gindullina et al.):** *"The allocation of the "Position of the epidemic peak" class as a separate category is consistent with literature data, which highlights this parameter as essential to epidemiological forecasting."*

Paper A justifies Class 4 (peak position) by literature salience — but a peak's *time* is a slot on the incidence-curve class, not a distinct class of comment. Under Paper B's rule, Class 4 would be a slot-value «target=peak-timing» attached to Class 1 (curve behavior), unless Class 4 requires different slots than Class 1. Concretely, Class 4's modifications («Add offset to desired peak day in term2», «Add penalty for discrepancy in infected count during peak in term2») operate on the *same* term as Class 1 (term2 = infected compartment). Structurally, this is one class with a slot-typed target. Splitting it into a separate class multiplies the ontology's arity without adding restrictions — exactly what Paper B §4.5 warns against. (Comparative inference)

## 8. Naming and evolution: SIRD term1..term4 as opaque aliases

Paper B §6 and §4.1 emphasize naming and evolution: a class name should reflect the concept, not obscure it; the hierarchy should evolve as domain understanding evolves.

> **Quote (Noy & McGuinness):** *"Classes represent concepts in the domain and not the words that denote these concepts. ... Maintaining a consistent class hierarchy may become challenging as domains evolve."*

> **Quote (Gindullina et al.):** *"Each term represents a specific compartment: term1 (susceptible), term2 (infectious), term3 (dead), term4 (recovered)."*

Naming: «term1..term4» is an opaque alias for a well-established SIRD taxonomy (Susceptible, Infectious, Recovered, Dead). Under Paper B's naming rule, the class names should be the domain terms (`Susceptible_penalty`, `Infectious_penalty`), and the LLM's prompt should refer to them by their epidemiological names — which are shorter, more mnemonic, and less prone to being «literally inserted» as numeric-looking labels. This is a small but real source of the literal-number confusion Paper A documents. (Comparative inference)

## Direction 1. Rebuild Table A.2 through Noy-McGuinness 7 steps

**Pipeline stage.** §2.2 Hierarchical text classifier + Appendix A ontology + Future work modification templates.  
**Mechanism.** Redo the ontology construction as a 7-step Noy-McGuinness pass:
1. Write competency questions (10–15 minimum) that the ontology must answer — e.g., «given a peak-shift comment, which loss term is modified, in what direction, and what integrity constraints are preserved?».
2. Survey and consider SNOMED, ICD-11, PINN loss taxonomies (Cuomo 2022 survey, Krishnapriyan 2021), SIRD compartment names.
3. Enumerate terms from **real** epidemiologists at the Smorodintsev Research Institute (per Paper A's own Future-work commitment), not from a synthetic LLM corpus.
4. Class hierarchy: allow multiple inheritance for mixed-intent comments; audit for singleton subclasses; audit for >12 subclasses.
5. Slot definitions on modification objects: `target_term` (enum over SIRD), `operator` (AddPenalty / Reweight / ShiftPeak / …), `numeric_parameter`, `preserved_constraints`.
6. Slot facets: cardinality (single or bounded multi), value-type (typed enum vs bounded float), range (per-term admissible interval).
7. Instances: canonical comment ↔ modification pairs, curated on a live ontology.
**Failure modes addressed.** Table A.2 «insufficient detail» (Author-stated by Paper A); literal number insertion; single-class-per-comment loss of mixed intent; circular synthetic training. (Speculative extension)

## Direction 2. Slot-facet-typed LLM prompt

**Pipeline stage.** §2.3 PINN Customizer (prompt construction) + LLM output validation.  
**Mechanism.** Instead of «Add penalty to term2» as prose, ship the LLM a JSON slot-and-facet structure and require its output to match:
```json
{"class": 1, "subclass": 1, "modification": {
  "target": "Infectious",  "operator": "AddPenalty",
  "penalty_type": "L2",    "coefficient": 0.5,
  "coefficient_range": [0.01, 5.0],
  "preserves": ["non_negativity", "monotonic_cumulative"]
}}
```
Validate outputs against the facet schema before compile-check. This is constrained-decoding-lite: the LLM cannot literally paste «7-10 days» into `coefficient` because the facet type is a bounded float.  
**Failure modes addressed.** literal number insertion; unused variables (schema doesn't admit dangling fields); comment-class / modification-target mismatch (validator can flag `target != class_default_target`). Ties to `19_wei_…` Direction 1 (feature-vector encoding) and `20_zhang_…` Direction 1 (Modification Quality Model). (Speculative extension)

## What not to transfer

Paper B is a wine-and-food tutorial in a Protégé-2000-style frame-based system; do not import Protégé specifics (frame syntax, Chimaera diagnostics, name-space conventions). The 7-step methodology is domain-agnostic; the wine/food examples are illustrative. Do not treat multiple inheritance as universally required — for some comment types, single-class assignment is genuinely correct (`Class 2: measures`), and the choice depends on domain. And do not conflate an ontology built for information sharing with an ontology built for LLM-prompt constraint — the latter has a stricter demand on facet completeness because LLMs will happily emit malformed values that a human would silently fix. (Comparative inference)

## Concrete next experiment

**Hypothesis.** Redesigning Table A.2 as a Noy-McGuinness slot-and-facet ontology and shipping its schema to the LLM as structured JSON (Direction 2) will reduce literal-number-insertion failures on Paper A's 20 comments × 3 LLMs = 60 modifications from the currently observed rate to near-zero, without lowering compile pass rate below the current 100/50/80% single-shot baseline.

**Protocol.**
1. Rewrite Table A.2 as facet-typed slots (per Direction 1). Publish schema JSON.
2. Modify PINN Customizer prompt: append «You must respond with JSON matching the following schema: …».
3. Rerun 20 comments × 3 LLMs.
4. Post-process each LLM output through schema validation before compile-check.
5. Compare against baseline: (i) count of literal-number failures; (ii) compile pass rate; (iii) MAE-based compliance rate; (iv) unused-term rate.

**Expected signal.** Literal-number failures should drop from ≈100% of numeric-mentioning comments to <10% (the LLM can no longer paste raw digits into a bounded-float slot). Compile pass rate should remain within ±5 percentage points of baseline. Compliance rate should either stay flat or improve slightly (schema doesn't add capability, only removes malformed outputs). ## Conclusion

Paper B is not about PINN or LLMs; it is a 20-year-old baseline methodology for how a first ontology should be built. Paper A's Table A.2 + Appendix A is exactly a first ontology — but built without Steps 1, 2, 5, 6, or iteration, and with Class 3 arguably violating Paper B's «introduce a subclass only if it has different slots/restrictions» rule. Each of Paper A's admitted failures — literal number insertion, unused variables, prompt-rule opacity — maps back to a specific Noy-McGuinness step that was skipped. The upgrade is remarkably cheap: no new algorithms, no new training data — a redesign of the modification schema as slot-typed facets, plus JSON-schema-validated LLM output. Paper A's Future-work commitment to «class-subclass-specific modification templates» is best executed as this Noy-McGuinness pass, not as tighter English rules.
